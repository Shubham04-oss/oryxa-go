# First live test: findings (2026-09-30)

Two accounts in the Oryxa workspace wired to the sandbox Slack workspace: Apollo mail (`shubham@oryxa.uk`) asked, and Shubham Tanwar (`shubham@oryxa.in`, admin) held a "Just you" note.

**What works, end to end in production:**
- **The Slack ask** at 03:31 UTC. The mention became an ask, Oryxa DMed the owner, the owner approved "AI summary only", the holder's agent ran, the guard came back clear (strict), and the answer was posted in the thread. About 45 s, 35 of them waiting for the owner.
- **The web request** with tool access at 03:25 UTC. It was approved, and the holder's agent answered "14 October" from the note.

Then the owner tried to break it. It broke in the places below, and each has evidence from the logs.

## P1

1. **Slack's DM buttons fail (Slack reports 403), so approval only works in the Oryxa app.**
   - **Evidence:**
     - During the test, no request reached `POST /v1/apps/slack/interactivity`, while `POST /v1/apps/slack/events` served 10 × 200.
     - A Slack-signed test request to the interactivity URL returns 200 through Cloudflare.
     - So the 403 is outside our origin: Slack is posting button clicks somewhere else.
   - **Likely cause:** the Slack app's Interactivity Request URL is not `https://api.oryxa.in/v1/apps/slack/interactivity`. An `app.oryxa.in` or `/v1/internal/...` address would answer 403.
   - **Fix:** in the Slack app, go to Interactivity & Shortcuts, set the Request URL to exactly that address, and save. If it's already right, capture Slack's exact error text.
2. **In the web app, the asker never sees the answer where they asked.**
   - **Cause:**
     - `interactiondelivery` delivers `requester_completed` into "the request's stable conversation for this recipient". That's a new thread created for the request (`waker.start`), not the conversation the asker filed the request from.
     - The asker's timeline doesn't render `type:"request"` items (a known follow-up).
     - The answer is visible only in Requests → Sent.
   - **Fix:** record the originating thread on the request and deliver the result into it, or put a request card with the answer into that chat. Then render request items in the timeline.
3. **The asking agent filed an information request without tool access.**
   - **What happened:** the first web request asked "share details about Project Falcon" with no requested tools. The holder approved, and the holder's agent answered "no tools were allowed, so no information could be retrieved."
   - **Fix:**
     - When a request asks for information, request `knowledge` by default.
     - On the holder's card, make Approve (with the requested tools) the obvious choice, and say plainly that "Approve without tools" means the agent can't look anything up.

## P2

4. **The consent guard held a correct answer as ungrounded.**
   - **Evidence:** in the "Allow for 1 hour" ask at 03:34, the answer ("launches 14 October, related to the newest AI launch") was held with `UNGROUNDED` (grounded 0.23, relevant 0.87). The owner had to review it, and only the Oryxa app offers that.
   - **Check:** what the guard saw as sources compared with the note's text. Then tune the grounding minimum on real asks, as slack-implementation.md §5 planned.
5. **The loop feels fixed, with too little human involvement.** Things the owner can't do:
   - edit the drafted answer before it's shared;
   - add a note;
   - talk to the asker.

   The asker can't follow up in the thread, and the bot's messages are all templates.
   - **Direction:**
     - The owner can edit or redraft the answer, in the DM and in the app.
     - A follow-up in the thread continues the same ask.
     - The owner can reply with a short note alongside the answer.
6. **Refusals read as silence.**
   - Slack refusals are ephemeral and vanish on reload.
   - A plain-text "@name" isn't a mention, which ends as `no_owner`.
   - Naming someone who resolves to the asker also ends as `no_owner`, with no hint.
   - **Fix:** keep the reason private, but also react on the asker's message so they notice. Use clear copy for each reason, e.g. "Mention the person by picking them from the list."

## P3

7. **The knowledge-base name field took the whole fact,** and nothing prompts you to add content after creating one, so the knowledge base stayed empty.
8. **A red "Failed" appears on a tool group** whose answer was fine: "12 tool calls · Failed". It alarms the member, and no failing tool shows in the Go logs.
9. **Most early refusals were identity:** `not_member` or `owner_not_member`, where the Slack email doesn't match the Oryxa email. Since #159 the router logs why ("a Slack user is not a member", with `why`), so the next one is self-explanatory.
